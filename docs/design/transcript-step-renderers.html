Transcript steps: renderers per tool

Each tool gets a step renderer. It decides three things: the title and argument chips (what the model asked for), the live sub-items shown while the call runs (temporary progress), and the completion summary (the one line that stays). Tools without a renderer use the generic one, so the transcript still looks consistent.

1 · Live, in context

While a turn is running, the active step shows under “Working…” even when the group is collapsed. Its sub-items stream in and then fold away when the call completes, leaving only the summary. After the turn ends, the group collapses to the usual “Worked for 6s” line.

2 · Anatomy of a step

Uses the existing ActivityStepRow metrics: 16pt glyph column, 13pt semibold title, 12pt faint meta. Two new slots: argument chips and the live rail.

1Glyph + state. The tool's glyph appears in markdown-heading blue. While the call runs, a spinner replaces the meta text instead of the glyph, so you can still tell which tool is running.
2Title. A verb phrase from the renderer, such as “Searching the web” while running and “Searched the web” when done.
3Argument chips. Structured input from the model: queries, filters, ranges, paths. These stay after completion.
4Live rail. Temporary sub-items from tool_call_progress. Each one is waiting, running, done, or failed. The rail folds away on completion, but you can bring it back by expanding the step.
5Meta. A running timer, then the final duration. Can also show a ×3 count, a cached badge, or a progress fraction.

Every renderer goes through the same states. Web search is the example here.

4 · How the live rail collapses

One web search with two queries, shown frame by frame. Sub-items appear as progress events arrive. On tool_call_complete the rail fades and shrinks (0.3s ease-out, or an instant swap with Reduce Motion), and the summary line takes its place.

5 · Tool gallery: running vs. done

Each pair shows the same call twice: on the left while it runs (with the live rail), on the right after it completes (summary only).

6 · Repeated calls and expanded history

Consecutive calls to the same tool still merge into one ×n row. When expanded, each child call keeps its own argument chips and summary, and you can replay a finished call's live rail as a read-only log.

7 · How it plugs in

Plugins are TypeScript only and can't ship SwiftUI, so they don't send views. They choose a presentation kind and send structured progress. Toby.app maps each kind to a native renderer.

Event contract (packages/core · chat-events.ts)

// existing — keep args structured through the reducer
{ type: "tool_call_start", blockKey, toolName, args }

// NEW — transient, replaces items by id; not persisted verbatim
{ type: "tool_call_progress", blockKey, seq,
  items: [{ id: "q1", label: "EU AI Act enforcement",
            state: "running" | "done" | "waiting" | "failed",
            detail?: "8 results", icon?: "globe", url? }],
  fraction?: 0.4 }

// existing — plus an optional renderer-shaped summary
{ type: "tool_call_complete", blockKey, result,
  presentation?: { summary: "8 results",
                   sources?: [{ title, url }] } }

Native side (Toby.app · Features/Chat/StepRenderers/)

protocol ToolStepRenderer {
  static var kind: ToolPresentationKind { get }
  func title(for s: ToolStepState) -> String
  func argChips(_ args: ToolArgs) -> [ArgChip]
  func liveItem(_ item: ToolProgressItem) -> LiveItemModel
  func summary(_ r: ToolResult) -> StepSummary
}

enum ToolStepRendererRegistry {
  // 1. exact tool name   (webSearch → WebSearchRenderer)
  // 2. manifest kind     (search / read / write / fetch / list …)
  // 3. GenericRenderer   (humanized label + key:value chips)
  static func renderer(for step: WorkStep) -> any ToolStepRenderer
}
